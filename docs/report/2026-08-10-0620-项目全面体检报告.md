## 1. 架构现状

### 1.1 分层模型

项目是一个**浏览器内的 iOS 模拟器 + AI 角色扮演平台**，采用四层结构：

```
┌─────────────────────────────────────────────────────────────┐
│  src/apps/          16 个 App（53,331 行 / 53%）            │
│  XingYu 可爱信 14k · Settings 9.4k · AIAppBuilder 5.5k ...  │
├─────────────────────────────────────────────────────────────┤
│  src/shell/         Device Shell（13,229 行）               │
│  Device · Springboard · AppHost · AppSwitcher · LockScreen  │
│  StatusBar · ControlCenter · DynamicIsland · Widgets        │
├─────────────────────────────────────────────────────────────┤
│  src/system/        iOS 设计系统组件（2,067 行）            │
│  AppScreen · NavBar · List · Material · Toast · Banner ...  │
├─────────────────────────────────────────────────────────────┤
│  src/platform/      跨层基建（30,634 行）                   │
│  ai/ · userApp/ · stores/ · storage/ · gesture/ ·           │
│  design-tokens/ · services/ · perf/                         │
└─────────────────────────────────────────────────────────────┘
```

分层契约写在各层 `CLAUDE.md` 里，且**确实被遵守的部分**：

- `system/ → apps|shell` 依赖 **0 处**（设计系统保持纯净，这是最难做到的一条，做到了）
- `apps/ → shell` 仅 **2 处**（`WallpaperPage` 和 `DemoApp` 引 `apps.data`）
- Shell 子组件互不 import，统一由 `Device.tsx` 编排——规范落实到位

### 1.2 三个核心子系统

**(a) App 运行时（`platform/userApp/`）** — 项目最有价值的架构资产。

```
TSX 源码字符串
  → compileTsx (Sucrase, 动态 import, 带 inline sourcemap)
  → executeInSandbox (new Function + 遮蔽 10 个全局变量 + 注入 require/React)
  → moduleResolver (白名单 @hiphone/* 12 个 SDK 模块 + 相对路径多文件解析)
  → appRegistry.register
  → AppScene 渲染
```

安装链路 `installer.install` 完成 manifest 校验 → 编译 → IDB 持久化（`app-meta` / `app-src` / `app-kv`）→ store 更新 → registry 注册。内置 user app（如 translate）通过 Vite `?raw` 走**完全相同**的链路，既保证 SDK 上限被真实验证，又让源码享受 IDE/TS/ESLint——这是一个很聪明的设计决策。

**(b) AI 对话基建（`platform/ai/`，33 源文件 / 39 测试文件）** — 密度最高、测试最充分的模块。

四段式 prompt 组装（System → History → App 协议 → Post-history）**明确围绕 LLM 服务商 KV cache 命中率设计**，`ai/CLAUDE.md` 里把"什么放哪一段"写成了硬规则。配套能力：三级 fallback 回复解析、记忆压缩三 pass 流水线、ReAct 心跳 agent（Web Worker 定时器规避后台节流）、工具注册表（含 `dynamicContext` 尾部注入）、AI-AI 对话引擎、OpenRouter 厂商路由。

**(c) 存储与多实体数据（`platform/storage/`）**

IndexedDB v6，7 个 object store。设计上分两类：
- **KV store** — zustand persist blob（18 个 key）
- **per-record store** — messages / moments / characterMemory / memoryState，通过 `zustandIdbSync` 做引用 diff 增量写入，避免全量序列化

`EntityStoreRegistry` 实现"每个角色一份独立数据"——玩家用原 key，AI 角色用 `::char-{id}` 后缀，支撑"查看别人的手机"这个核心玩法。`dataPortability` 做全库 ZIP 导出/导入，**store-agnostic**（直接遍历 object store），新增 store 不需要改导出逻辑——设计正确。

### 1.3 数据流总览

```
用户操作 → App 组件 → zustand store (39 个)
                          ↓ persist middleware
                       idbStorage (KV) / idbRecordStorage (per-record)
                          ↓
AI 心跳 (30s tick) ─→ heartbeatAgent ReAct 循环 ─→ heartbeatTools
                          ↓ 读写
                       XingYu 消息 / Notes / 记忆 / 签名
                          ↓
                    promptAssembly → chatComplete → LLM 厂商 (浏览器直连)
```

## 2. 现有问题

### P0-1 🔴 质量门禁完全缺失：lint 坏了，CI 不存在

```
$ pnpm lint
ESLint couldn't find an eslint.config.(js|mjs|cjs) file.  → exit 2
```

`package.json` 里配了 `lint` script、装了 `eslint@10` + `typescript-eslint` + `eslint-plugin-react-hooks`，**但配置文件从来不存在**（全仓库 `eslint.config.*` 和 `.eslintrc*` 均无）。这意味着：

- `react-hooks/exhaustive-deps` 从未跑过——项目里 27 处 `addEventListener`、7 处 `setInterval`、大量 `useEffect` 手写依赖数组，**没有任何工具在检查依赖遗漏**
- 没有 `.github/workflows/`，typecheck / test / build 全靠人在本地记得跑

**影响**：这是所有其他问题的放大器。规模到了 10 万行，靠自律维持质量的成本会指数上升。

### P0-2 🔴 platform 层反向依赖 apps 层（35 处）

`platform/` 本应是"被所有层消费、不消费任何上层"的基座，实测：

| platform 文件 | 依赖的 app |
|---------------|-----------|
| `ai/aiChatEngine.ts` | XingYu ×4 |
| `ai/heartbeatTools.ts` | XingYu ×3 + Notes ×2 |
| `ai/heartbeatAgent.ts` | XingYu ×3 |
| `ai/memoryWriter.ts` | XingYu ×4 |
| `ai/buildMemoryEntry.ts` | XingYu ×1 |
| `ai/heartbeatVirtualWorldStory.ts` | XingYu ×2 |
| `ai/deviceContext.ts` | Weather ×2 |
| `storage/zustandIdbSync.ts` | XingYu (Message/Moment 类型 + 硬编码 messages/moments 字段) |
| `storage/idbRecordStorage.ts` | XingYu |
| `userApp/sdk/ai.ts` | XingYu |

合计 `@/apps/XingYu` **30 次**、`@/apps/translate` 12 次、`@/apps/Weather` 5 次、`@/apps/Notes` 2 次。

**后果**：
1. `platform/ai` 不是"AI 基建"，是"XingYu 的 AI 后端"。第二个聊天类 App 出现时，要么复制一份，要么大改。
2. `zustandIdbSync` 直接 hardcode 了 `messages` / `moments` 两个字段名，其他 store 想要增量同步只能重写。
3. 循环依赖风险：`apps/XingYu` 也在用 `platform/ai`，形成 platform ↔ apps 双向环。目前靠 ESM 惰性求值没炸，但这类环在重构时会以"初始化顺序诡异 bug"的形式爆发。

### P0-3 🔴 持久化数据没有迁移契约

18 个持久化 key，**只有 4 个**声明了 `version` + `migrate`（`aiConfigStore` v3、`springboardLayoutStore` v4、`musicDataStore` v4、`memoryStateMigration` v1）。剩下 14 个（含 `hiPhone-xingyu`、`hiPhone-characters`、`hiPhone-photos`、`hiPhone-presence`、`hiPhone-heartbeat`、`hiPhone-world-books`、`hiPhone-xingyu-stickers` 等）**一旦改字段结构，老用户数据直接进入未定义行为**。

`docs/human_todolist.md` 里"多身份系统"决策 3 明确写着"无需数据迁移——直接改结构，老数据清空重来即可"。在只有开发者自己一个用户时这是合理的；一旦真实用户产生了几个月的角色记忆和聊天记录，"清空重来"就不再是选项。而且 `musicDataStore` 的 `migrate: () => ({})` 就是"版本不对直接丢弃全部数据"——这个模式如果被复制到记忆/聊天 store 上会是灾难。

**note**：全库 ZIP 备份（`dataPortability`）能兜住"用户主动备份"的场景，但兜不住"升级后静默数据损坏"。

### P1-1 🟠 前端包体 3.15 MB 单 chunk，零代码分割

```
dist/assets/index-*.js         3,149 KB │ gzip: 903 KB   ← 全部业务代码
dist/assets/index.global-*.js    279 KB │ gzip:  72 KB   ← @tailwindcss/browser
dist/assets/esm-*.js             201 KB │ gzip:  46 KB   ← sucrase
PWA precache: 111 entries / 7,330 KB
```

全项目 **`React.lazy` 使用次数 = 0**，动态 `import()` 只有 2 处（sucrase、tailwind browser 运行时）。原因是 `registerBuiltins()` 在模块加载期静态 import 全部 16 个 App：

```ts
// src/apps/registerBuiltins.ts —— 在 App.tsx 模块作用域被调用
import { SettingsApp } from './Settings/SettingsApp';
import { XingYuApp } from './XingYu/XingYuApp';
... 16 个
```

于是 leaflet（地图）、@tiptap 全家桶（备忘录富文本）、motion、lucide 全图标库、16 个 App 全部进首屏。**这是一个自称"适配主流手机型号"的移动端 Web 应用**——4G 下 903 KB gzip 首包约 3-5 秒，且 PWA 首次安装要拉 7.3 MB。

架构上其实已经为分割做好了准备：`appRegistry` 存的是 `component: ComponentType`，只要改成 `loader: () => Promise<ComponentType>` + `React.lazy`，即可按需加载，无需改动 `AppScene` 以外的调用方。

### P1-4 🟠 用户 App 沙箱是 L1 软沙箱（已知且已记录）

`sandbox.ts` 通过 `new Function(...SHADOWED_GLOBALS, code)` 用参数名遮蔽 10 个全局变量。`userApp/CLAUDE.md` 诚实地写明："**不是对抗性安全边界**，逃逸路径存在（`constructor.constructor('return this')()` 等）"。

当前语境（用户自己写自己的 app）风险可接受。但项目已经有 **App Store + ZIP 上传安装 + AI 工坊自动生成 app** 三条链路——一旦出现"用户之间分享 app 包"的场景，一个恶意 app 可以：读取 IndexedDB 里的全部聊天记录和角色记忆、**窃取 `aiConfigStore` 里明文存储的 API Key**、向任意端点发请求。

配套问题：**LLM API Key 明文存在 IDB**（`hiPhone-ai-config`），且浏览器直连厂商端点。BYOK 客户端应用这是常规做法，但与 L1 沙箱叠加后，"沙箱逃逸"的收益从"读数据"升级为"偷用户的钱"。

## 3. 长期演进方向

分三个视野（Horizon）。H1 是止血，H2 是解耦，H3 是平台化。**建议严格按顺序**——H2 的重构没有 H1 的门禁兜底会非常危险。

### H1 — 建立自动化门禁（1-2 周，最高优先级）

目标：**让"改坏了"这件事由机器发现，而不是由用户发现**。

1. **补 `eslint.config.js`**（flat config），最低配置：`typescript-eslint` recommended + `react-hooks/exhaustive-deps` + `no-restricted-imports`。
   - 关键收益是 `no-restricted-imports`：把 P0-2 的分层规则**变成机器可执行的约束**
     ```js
     // src/platform/** 禁止 import @/apps/**
     // src/system/** 禁止 import @/apps/** 和 @/shell/**
     // src/shell/** 禁止 import @/apps/**（AppScene 白名单例外）
     ```
   - 先用 `warn` 级别把 35 处存量标出来，新增的一律 `error`，存量按 H2 节奏清理
2. **加 `.github/workflows/ci.yml`**：`typecheck` → `lint` → `test` → `build` 四道门，PR 必过。
3. **测试提速**：`test.pool: 'threads'` + `isolate: false` 试跑，或按目录拆分 `test:unit` / `test:app`，把 158s 压到 60s 以内——**慢测试会被绕过，快测试才会被跑**。
4. **skip 治理**：把 `iconGrid.dragPreview` 那条从 `it.skip` 改成 `it.fails`（vitest 支持），让已知回归在测试报告里**可见**而不是消失。
5. **仓库清理**：`git rm -r --cached output .superpowers`，`__dirname` → `import.meta.dirname`。

### H2 — 解耦与治理（1-2 个月）

**2.1 抽出 `platform/ai` 的 App 无关内核**

把 XingYu 特有的部分推到一个"聊天宿主适配器"接口后面：

```ts
// platform/ai/hostAdapter.ts —— platform 只认接口，不认 XingYu
export interface ChatHostAdapter {
  appId: string;
  listConversations(charId: string): ConversationRef[];
  appendMessage(convId: string, msg: PlatformMessage): void;
  listStickers(charId: string): StickerRef[];
  renderMemoryEvent(evt: ToolEvent): string;
}
export function registerChatHost(a: ChatHostAdapter): void;
```

XingYu 在 `registerBuiltins` 时注册自己的实现。这样：
- `platform/ai` 的 30 处 XingYu import 归零，platform ↔ apps 的环打破
- 第二个聊天类 App（微信/Snapchat 风格）可以复用整套 AI 基建
- `heartbeatTools` 从"操作 XingYu"变成"操作已注册的 host"，工具集自动跟随

同样地把 `zustandIdbSync` 泛化为 `createRecordSync({ storeName, selectors })`，让任何 store 都能声明式接入增量持久化。

**2.2 建立持久化迁移契约**

- 为全部 18 个持久化 key 补 `version` + `migrate`，**未声明 version 的 store 在 CI 里报错**（写一条 lint 规则或一个测试）
- 禁止 `migrate: () => ({})` 这种丢弃式迁移出现在含用户内容的 store（记忆 / 消息 / 角色 / 照片）
- 每次 `DB_VERSION` bump 配一条升级路径测试（`fake-indexeddb` 已经装了，基础设施现成）

**2.3 拆解 XingYu**

`xingYuDataStore` 1,451 行按领域切成 4 个 slice：`conversations` / `messages` / `moments` / `profile`，用 zustand slice 模式组合。`ChatDetail.tsx` 1,757 行按"消息列表 / 输入栏 / 引用面板 / 长按菜单"拆分。**拆之前先补测试**——当前 45:11 的覆盖比不足以支撑安全重构，建议先把 store 的 40+ 个 action 用单测锁死（这类纯逻辑测试写得快、价值高）。

**2.4 首屏包体分割**

`AppRegistryEntry.component` 改为 `loader: () => Promise<{ default: ComponentType }>`，`AppScene` 用 `React.lazy` + `Suspense`（fallback 直接复用现有的 App 启动动画）。预期主 chunk 从 3.15 MB 降到 800 KB 以下，leaflet / tiptap / 各 App 按需加载。这是**改动面最小、收益最大**的性能优化——registry 抽象已经就位，只需改 registry 的类型和 AppScene 一处消费点。

**2.5 i18n 落地**

按已写好的 plan 执行，但**顺序建议调整**：先做 AI prompt 层的 i18n（`promptAssembly` / 工具描述 / 记忆模板），再做 UI 层。原因是 prompt 层文件少（~10 个）但改造最难，且它决定了"AI 角色能不能说英文"这个产品级能力；UI 层文件多但是机械替换，可以用脚本半自动化。

### H3 — 平台化（3-6 个月）

**3.1 沙箱升级到 L2（iframe + postMessage）**

`userApp/CLAUDE.md` 已经预留了升级路径（"ModuleResolver 可跨 iframe 序列化"）。触发条件是**"用户之间开始分享 app"**——在那之前不必做，在那之后必须做。配套：
- API Key 不再暴露给 app，`@hiphone/ai` 走宿主代理，宿主负责计费/限流/审计
- 每个 app 声明 `permissions`（storage / ai / network / notification），安装时展示，运行时强制

**3.2 API Key 的服务端代理选项**

保留 BYOK 直连（隐私优先、零成本），同时提供可选的 Cloudflare Functions 代理路径（`functions/` 已有基础设施）。收益：Key 不落浏览器、可加请求日志和用量统计、可规避部分厂商的 CORS 限制。

**3.3 文档体系重构：从"流水账"到"知识库"**

保留 `docs/plan/` 作为历史档案（不再增长为主要载体），新增：

```
docs/architecture/
  README.md              ← 架构总览 + 索引（唯一入口）
  layering.md            ← 四层契约与依赖规则（与 eslint 规则互为文档）
  app-runtime.md         ← 编译/沙箱/SDK/安装链路
  ai-pipeline.md         ← prompt 四段式 / 记忆压缩 / 心跳 agent
  persistence.md         ← IDB schema / 迁移契约 / 多实体隔离
  multi-entity-data.md   ← 已存在
```

规则：**架构决策变更时改 architecture 文档，plan 只记录"这次做了什么"**。同时合并 `CLAUDE.md` / `AGENTS.md` 双份规范（保留一份，另一份用 symlink 或一行引用）。

**3.4 端到端测试**

当前 1745 条全是单测/组件测试，**没有任何 E2E**。项目的核心价值链路（解锁 → 打开 App → 与 AI 聊天 → 心跳产生记忆 → 切换视角看角色的手机）跨越所有 4 层，单测无法覆盖。Playwright 在这个环境已预装，建议用 mock LLM 端点跑 5-8 条关键路径的冒烟测试，接进 CI。

**3.5 法务出清**

- AI 生成一套原创图标替换苹果原版（secretary 已立项）
- 评估项目名 / PWA manifest 中 "hiPhone" 与苹果商标的关系
